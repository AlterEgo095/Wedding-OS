  5238→### 12. How wedding creation sets the theme
  5239→
  5240→**3 entry points** (no `/api/weddings/route.ts` exists — the brief was speculative):
  5241→
  5242→#### (a) `/api/platform/weddings` POST — basic admin CRUD
  5243→- Creates Wedding row only (slug, brideName, groomName, coupleLabel, weddingDate, timezone, venueName, venueCity, status, plan, isDefault=false, publishedAt)
  5244→- **Does NOT create a Theme row.**
  5245→- **Does NOT create a Settings row.**
  5246→- First `GET /api/theme` will return `DEFAULT_THEME` constants (classic-gold values) with `customizations: null` because `db.theme.findUnique` returns null.
  5247→- Theme row is created lazily on first `PUT /api/theme` (upsert create branch) or first `POST /api/theme/apply-template`.
  5248→
  5249→#### (b) `/api/platform/weddings/[id]/duplicate` POST — duplication
  5250→- Copies source Wedding → new Wedding (DRAFT, TRIAL, isDefault=false)
  5251→- Copies Settings (key/value pairs verbatim)
  5252→- **Copies Theme row** (`db.theme.create({ data: { weddingId, primaryColor, accentColor, fontDisplay, fontBody, layout, customizations } })`) — **`customizations` is copied verbatim, including any `penpot` integration blob from the source.**
  5253→- Copies MusicTrack (URL reference, no file copy)
  5254→- Copies EventTimeline + CoupleStory (text + image URLs, no file copy)
  5255→- Does NOT copy: guests, tables, media files, access logs, audit logs, subscriptions, invoices, invitations
  5256→
  5257→⚠️ **Subtle data leak**: duplicating a wedding duplicates its `customizations.penpot` blob, so the new wedding's PenpotStudio will show the source wedding's Penpot file as "Lié". The new couple would need to manually unlink + relink their own Penpot file. The Collection Engine should consider clearing/nullifying `customizations.penpot.fileId` + `fileUrl` on duplication (keep `tokens` only).
  5258→
  5259→#### (c) `/api/onboarding/create-wedding` POST — onboarding wizard (transactional)
  5260→- Atomic `db.$transaction` creating 6 entities: Wedding, 15 essential Settings rows, AdminUser (ORGANIZER), Subscription (PENDING_PAYMENT), Invoice (OPEN), 3 AuditLogs
  5261→- **Does NOT create a Theme row.**
  5262→- Seeds Settings `primary_color: '#D4A853'` (legacy Setting, NOT the Theme table)
  5263→- Seeds Settings `music_enabled: 'false'`, `music_volume: '0.30'`
  5264→- The Settings `primary_color` is NOT consumed by /api/theme (which reads from the Theme table, not Settings). It's a vestigial Setting from the pre-Phase-1 single-tenant era.
  5265→- Onboarded wedding's `GET /api/theme` returns DEFAULT_THEME (classic-gold) until the organizer opens ThemeCustomizer and either saves or applies a template.
  5266→
  5267→**Summary**: NONE of the 3 wedding-creation routes pre-create a Theme row. The Theme row is created lazily on first theme edit. This means **the 4 THEME_TEMPLATES are NOT auto-applied at wedding creation** — the default wedding "looks like" classic-gold only because DEFAULT_THEME constants happen to match classic-gold's values.
  5268→
  5269→**Implication for Collection Engine**: there is a clear insertion point — wedding creation (any of the 3 routes) could accept a `templateId` / `collectionId` param and pre-create the Theme row with that template's values + link the corresponding Penpot file. This would make the "Penpot as Template Factory" workflow seamless: pick a collection at onboarding → wedding starts with both the canonical theme fields AND a pre-linked Penpot file ID.
