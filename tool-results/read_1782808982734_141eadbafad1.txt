  4313→## 3. Token / QR logic (AES-256-GCM + JWT)
  4314→
  4315→### File: `src/lib/guest-auth.ts` (428 LOC)
  4316→
  4317→#### Encryption (used for invitation link tokens)
  4318→```ts
  4319→const ENCRYPTION_ALGORITHM = 'aes-256-gcm';
  4320→const IV_LENGTH = 16;
  4321→const TAG_LENGTH = 16;
  4322→
  4323→function getEncryptionKey(): Buffer {
  4324→  return crypto.createHash('sha256').update(ENCRYPTION_KEY).digest(); // derives 32-byte key
  4325→}
  4326→
  4327→export function encryptId(id: string): string {
  4328→  const key = getEncryptionKey();
  4329→  const iv = crypto.randomBytes(IV_LENGTH);
  4330→  const cipher = crypto.createCipheriv('aes-256-gcm', key, iv);
  4331→  let encrypted = cipher.update(id, 'utf8', 'hex');
  4332→  encrypted += cipher.final('hex');
  4333→  const tag = cipher.getAuthTag();
  4334→  // Format: iv:tag:encrypted (all hex)
  4335→  return `${iv.toString('hex')}:${tag.toString('hex')}:${encrypted}`;
  4336→}
  4337→```
  4338→- `ENCRYPTION_KEY` env var (falls back to `JWT_SECRET` or `'dev-encryption-key'`)
  4339→- IV is 16 bytes random per encryption (not reused)
  4340→- Auth tag is 16 bytes
  4341→- Format: `iv_hex:tag_hex:ciphertext_hex` (string, URL-safe via `encodeURIComponent`)
  4342→
  4343→**What is encoded**: the `invitationCode` string (e.g. `JOS-001` or whatever the couple configured). NOT the guestId, NOT any session data. The token is a stateless, tamper-evident proof that "someone with this invitationCode wants to authenticate."
  4344→
  4345→#### Token pair (separate from encryption)
  4346→- `generateInvitationLinkToken(invitationCode)` → `encryptId(invitationCode)` (alias)
  4347→- `decryptInvitationLinkToken(token)` → `decryptId(token)` (returns null on any failure)
  4348→
  4349→#### JWT (used for session tokens, separate from invitation link tokens)
  4350→- `generateGuestToken({guestId, sessionId, code, fingerprint})` → `jwt.sign(payload, GUEST_JWT_SECRET, {expiresIn:'30d'})`
  4351→- `GUEST_JWT_SECRET = (process.env.JWT_SECRET || 'dev-only-secret') + '-guest-session'`
  4352→- Stored in `guest_session` cookie (httpOnly, sameSite:lax, 30-day maxAge)
  4353→
  4354→#### QR code generation (server-side, `/api/guests/qrcode/[code]/route.ts`)
  4355→Library: `qrcode` npm package (`import QRCode from 'qrcode'`)
  4356→```ts
  4357→const qrDataUrl = await QRCode.toDataURL(qrUrl, {
  4358→  width: 300, margin: 2,
  4359→  color: { dark: '#000000', light: '#FFFFFF' },
  4360→});
  4361→```
  4362→**What is encoded in the QR**: a full URL, NOT the raw invitationCode.
  4363→- Default wedding: `${baseUrl}/?invite=${encryptedToken}`
  4364→- Tenant wedding: `${baseUrl}/w/${slug}/invite/${encryptedToken}`
  4365→
  4366→The encrypted token is the AES-256-GCM-encrypted invitationCode. The `/w/[slug]/invite/[code]/page.tsx` page receives it, calls `/api/guest/invite?token=...`, and auto-authenticates.
  4367→
  4368→#### Brute-force protection
  4369→- In-memory `Map<string, BruteForceEntry>` (resets on server restart — OK for SQLite-scale)
  4370→- `MAX_LOGIN_ATTEMPTS_PER_HOUR` = 10 (env override)
  4371→- `BRUTE_FORCE_BAN_MINUTES` = 60 (env override)
  4372→- Cleanup interval: every 10 minutes
  4373→- Cleanup is per-IP-subnet key (first 3 octets of IPv4)
  4374→
  4375→#### Fingerprint
  4376→`generateFingerprint(userAgent, ip)` = SHA-256 of `${userAgent}|${first3octets of IP}` → first 16 hex chars. Used to detect session hijacking (warns but does NOT block on mismatch — logs `FINGERPRINT_MISMATCH` action).

  4637→### Performance tier system
  4638→5 tiers: `ultra, high, medium, low, minimal`.   4721→## 11. GAPS identified for the Collection Engine
  4722→
  4723→### GAP-1: No Guest.tier field (HIGH PRIORITY for Invitation Pack)
  4724→The Guest model has `category` (5 values: VIP, FAMILLE, AMIS, SPONSORS, COLLEGUES) and `invitationType` (2 values: couple, individuel) but NO dedicated `tier` field. The InvitationCard renders the same design for every guest — only the badge color/icon changes.
  4725→
  4726→**Implication**: A Collection Engine that wants to ship a "VIP Pack" (premium invitation template + printed card + WhatsApp sticker) vs a "Standard Pack" (basic template + email only) needs a tier discriminator. Options:
  4727→- (a) Reuse `category` — quick but conflates guest relationship with prestige tier (a sponsor might be a VIP, a colleague might be VIP)
  4728→- (b) Add `tier` enum field to Guest (`STANDARD | VIP | PRESS | SPONSOR | FAMILY`) — cleanest, requires Prisma migration
  4729→- (c) Use a junction table `GuestInvitationPack` linking guests to packs — most flexible
  4730→
  4731→### GAP-2: Single fixed InvitationCard design (HIGH PRIORITY)
  4732→InvitationCard.tsx is ONE hardcoded JSX tree. There is no `templateId` prop, no template registry, no variant switch. The download-ready version in GuestPersonalSpace.tsx is ALSO a separate hardcoded JSX (different layout: 54%/46% split with side-by-side photos vs the on-screen vertical card).
  4733→
  4734→**Implication**: A Penpot Template Factory needs a render dispatcher — e.g. `<InvitationCardRenderer templateId="royal-gold" guest={...} settings={...} />` that picks among Penpot-backed templates (or falls back to the current fixed design). The current InvitationCard would become the "legacy" template.
  4735→
  4736→### GAP-3: No invitation template concept in DB
  4737→- No `InvitationTemplate` Prisma model exists
  4738→- No `templateId` field on Guest or Wedding
  4739→- Theme.customizations JSON currently stores `penpot: { fileUrl, fileId, pageId, invitationFrameId, saveTheDateFrameId, lastSyncedAt, tokens }` (per PENPOT-NATIVE-INTEGRATION worklog) but this is a SINGLE template per wedding — not per-guest-tier
  4740→
  4741→**Implication**: Need either a new `InvitationTemplate` model (id, weddingId, name, tier, penpotFileId, penpotFrameId, tokens) OR extend `Theme.customizations.penpot` to be an array of templates keyed by tier.
  4742→
  4743→### GAP-4: Dead Invitation model blocks "sent pack" tracking
  4744→The `Invitation` Prisma model (lines 390-402) has the right shape (`channel, recipient, guestId, status, sentAt`) for tracking "which guest received which pack via which channel" — but it has ZERO queries in the codebase. The sending infrastructure (SMS/EMAIL/WHATSAPP gateways) was never built.
  4745→
  4746→**Implication**: The Collection Engine's "Invitation Pack" dispatch flow needs to either:
  4747→- (a) Resurrect the `Invitation` model by wiring it to a new sending service, or
  4748→- (b) Replace it with a richer `InvitationPackDelivery` model that tracks pack template + tier + channel + status + per-channel metadata.
  4749→
  4750→### GAP-5: Media.category enum lacks Collection-Engine-relevant values
  4751→Current allowed categories: `GALLERY, COUPLE_STORY, DOCUMENT, OTHER`. Missing:
  4752→- `INVITATION_BG` — for template-bound background images
  4753→- `HERO` — for hero section backgrounds (currently the hero uses hardcoded `/couple-hero.png`)
  4754→- `SAVE_THE_DATE` — for save-the-date graphic assets
  4755→- `PRINT_PACK` — for print-resolution assets (300+ DPI) distinct from screen-resolution gallery photos
  4756→- `LOGO_MONOGRAM` — for couple monogram used on invitations
  4757→
  4758→**Implication**: Adding new enum values is a 2-line change in `/api/media/route.ts` lines 71 and 75. The schema itself is permissive (`category String?`) so no migration is needed — just update the validation array.
  4759→
  4760→### GAP-6: Two parallel visual-config stores, neither synced to DB
  4761→- `luxury-engine-store` and `visual-effects-store` both live in localStorage keyed by wedding slug
  4762→- Neither persists to the Theme model or any other Prisma table
  4763→- A Collection Engine "Pack" that bundles a luxury theme + effect presets with an invitation template cannot ship those presets to other devices/browsers for the same wedding
  4764→
  4765→**Implication**: Either accept that visual ambiance is per-browser (couples reconfigure on each device) or extend Theme.customizations JSON to optionally hold luxury + effects presets that hydrate the stores on first load.
  4766→
  4767→### GAP-7: No "Collection" or "Pack" abstraction
  4768→There is no Prisma model for a "Collection" (a bundle of templates + assets + settings). The Penpot integration (per prior worklog) is per-wedding, single-template. To support multiple packs per wedding (Invitation Pack, Print Pack, Save-the-Date Pack, Thank-You Card Pack), the schema needs a new model:
  4769→
  4770→```prisma
  4771→model CollectionPack {
  4772→  id           String   @id @default(cuid())
  4773→  weddingId    String
  4774→  type         String   // INVITATION, PRINT, SAVE_THE_DATE, THANK_YOU
  4775→  name         String
  4776→  templateId   String?  // references a Penpot frame
  4777→  tier         String?  // STANDARD, VIP, PRESS, etc.
  4778→  assets       String?  // JSON: { mediaIds: [], tokens: {}, ... }
  4779→  status       String   @default("DRAFT") // DRAFT, PUBLISHED, ARCHIVED
  4780→  createdAt    DateTime @default(now())
  4781→  updatedAt    DateTime @updatedAt
  4782→}
  4783→```
  4784→
  4785→This would be the spine of the Collection Engine.
  4786→
  4787→### GAP-8: Export pipeline is hardcoded to ONE design
  4788→`GuestPersonalSpace.tsx` has `downloadRef` pointing at an inline JSX tree (lines 357+) that is the ONLY thing html2canvas will capture. There is no way to point the export at a different template.
  4789→
  4790→**Implication**: For a Collection Engine that produces multiple pack artifacts (invitation PDF, save-the-date PNG, table card PDF), the export pipeline needs to be refactored into a reusable function: `exportPackArtifact(templateId, guest, settings, format)` that renders the right template off-screen and captures it. Currently this logic is inlined in a single component.
