   198→P0-SEC-1: Hardcoded JWT secret fallback enables admin token forgery
   199→FILE: src/lib/auth.ts:28
   200→PROOF:
   201→  let _jwtSecret: string | null = null;
   202→  function getJwtSecret(): string {
   203→    if (_jwtSecret !== null) return _jwtSecret;
   204→    const env = process.env.JWT_SECRET;
   205→    if (env) { _jwtSecret = env; return _jwtSecret; }
   206→    if (process.env.NODE_ENV === 'production' && ...) {
   207→      console.warn('WARNING: JWT_SECRET is not set in production! ...');
   208→    }
   209→    _jwtSecret = 'wedding-platform-dev-secret-key-not-for-production';
   210→    return _jwtSecret;
   211→  }
   212→  // generateToken() and verifyToken() both call getJwtSecret().
   213→IMPACT: The repo's committed .env defines only DATABASE_URL — JWT_SECRET is
   214→  unset. In production, getJwtSecret() silently falls back to the publicly-known
   215→  string 'wedding-platform-dev-secret-key-not-for-production' (only a console.warn
   216→  is emitted). Any attacker can sign a JWT with payload
   217→  {id:'x', role:'PLATFORM_ADMIN', weddingId:null, isPlatformAdmin:true} and call
   218→  ANY /api/platform/* route as platform owner: list/read/update/delete every
   219→  wedding, every AdminUser (incl. password reset), every invoice, every
   220→  subscription, and create new weddings/organizers. Total authentication bypass.
   221→FIX: Throw at module scope in production when JWT_SECRET is missing
   222→  (do NOT fall back to a constant). Add a startup self-check that fails the build
   223→  if the env var is absent.
   224→```

   247→P0-SEC-3: Hardcoded encryption key fallback enables invitation-link token forgery
   248→FILE: src/lib/guest-auth.ts:10
   249→PROOF:
   250→  const ENCRYPTION_KEY =
   251→    process.env.ENCRYPTION_KEY ||
   252→    process.env.JWT_SECRET ||
   253→    'dev-encryption-key';
   254→  function getEncryptionKey(): Buffer {
   255→    return crypto.createHash('sha256').update(ENCRYPTION_KEY).digest();
   256→  }
   257→  // encryptId/decryptId use AES-256-GCM with this key. Used to encrypt the
   258→  // invitationCode in /api/guest/invite and the lookupToken in /api/guest/lookup.
   259→IMPACT: With both ENCRYPTION_KEY and JWT_SECRET unset (current .env), the

   261→  attacker can (a) decrypt any encrypted invitation-link token they observe in
   262→  the wild (e.g. from a leaked WhatsApp message or QR code), recovering the

   270→FIX: Fail-fast in production if ENCRYPTION_KEY (or JWT_SECRET fallback) is unset.
   271→  Rotate the key + invalidate all outstanding encrypted tokens once fixed.

   274→```
   275→P0-SEC-4: Privilege escalation — non-platform-admin with null weddingId is
   276→treated as a platform admin by resolveAdminTenant
   277→FILE: src/lib/tenant-context.ts:279
   278→PROOF:
   279→  export async function resolveAdminTenant(request, user) {
   280→    // Non-platform admin: lock to their own wedding (ignore X-Wedding-Slug
   281→    // header to prevent cross-tenant access).
   282→    if (!isPlatformAdmin(user.role) && user.weddingId) {   // ← BUG: && short-circuits on null
   283→      // ... lock to user.weddingId ...
   284→      return { context: buildTenantContext(cached), ... };
   285→    }
   286→    // Platform admin: respect X-Wedding-Slug header or fall back to default.
   287→    const slug = extractSlugFromRequest(request) ?? DEFAULT_WEDDING_SLUG;
   288→    const wedding = await resolveWeddingBySlug(slug);
   289→    // ... returns context for ANY wedding the caller names via header ...
   290→  }
   291→IMPACT: If a non-platform-admin user (ORGANIZER / RECEPTION / CONTROLLER) has
   292→  weddingId = null in the DB, the condition `!isPlatformAdmin(role) && user.weddingId`
   293→  evaluates to `true && null` → falsy, and execution falls through to the
   294→  platform-admin branch. The user can then send X-Wedding-Slug: <any-wedding>
   295→  and operate on ANY wedding — read/write guests, tables, settings, media,
   296→  theme, music, timeline, couple-story, etc. They effectively become a
   297→  platform admin for all tenant-scoped APIs. weddingId is nullable in the
   298→  schema (schema.prisma:75 `weddingId String?`); the route
   299→  /api/admin/users POST (line 79) does `isPlatformAdmin(role) ? null :
   300→  (weddingId || context.weddingId)` which today always sets a value, but any
   301→  future code path (migration script, manual DB fix, partial rollback) that
   302→  leaves an ORGANIZER with weddingId=null silently grants them cross-tenant
   303→  access. The safe behavior is to REJECT, not fall through.
   304→FIX: Replace the guard with:
   305→    if (!isPlatformAdmin(user.role)) {
   306→      if (!user.weddingId) {
   307→        return { context: null, wedding: null,
   308→                 error: { status: 403, message: 'Account misconfigured: no wedding assigned' } };
   309→      }
   310→      // ... lock to user.weddingId ...
   311→    }

   315→P0-SEC-5: Unauthenticated guest PII enumeration + mass identity takeover via
   316→/api/guest/lookup (no rate limit) + /api/guest/auto-auth (lookupToken chain)
   317→FILE: src/app/api/guest/lookup/route.ts:19 (GET handler) +
   318→      src/app/api/guest/auto-auth/route.ts:19 (POST handler)
   319→PROOF:
   320→  // /api/guest/lookup — NO checkRateLimit() call anywhere in the file (verified
   321→  // by grep). Returns up to 30 + 100 (accent fallback) guest records per query,
   322→  // each including firstName, lastName, displayName, invitationType, seats,
   323→  // category, table name+number, AND a lookupToken bound to the requester's IP
   324→  // subnet (first 3 octets) with a 15-minute validity window.
   325→
   326→  // /api/guest/auto-auth — accepts a lookupToken, validates:
   327→  //   1. decrypts (subject to P0-SEC-3 weak-key bypass, but not required here)
   328→  //   2. not in usedLookupTokens (one-time, in-memory, cleared every 10 min)
   329→  //   3. age ≤ 15 min
   330→  //   4. IP subnet matches the issuer
   331→  //   → then issues a 30-day guest_session cookie for that guest.
   332→  // Rate limit: 5 calls/min/IP (easily defeated by IP rotation).
   333→
   334→IMPACT: An attacker who knows any wedding slug (publicly visible in URLs,
   335→  shareable, enumerable via /api/platform/weddings if combined with P0-SEC-1,
   336→  OR simply known from a shared invitation URL):
   337→  1. Calls /api/guest/lookup?q=aa, ?q=ab, … ?q=zz (676 queries, no rate limit)
   338→     → dumps the entire guest list of that wedding (names, tables, categories).
   339→  2. For each returned lookupToken, calls /api/guest/auto-auth from the same IP
   340→     within 15 minutes → receives a 30-day guest_session cookie for that guest.
   341→  3. With each session, reads the guest's full PII (phone, email, personal
   342→     message, invitation code, encrypted invite link) via /api/guest/me, AND
   343→     can POST /api/guest/rsvp to mass-DECLINE or mass-CONFIRM invitations,
   344→     sabotaging the wedding's headcount.
   345→  The "search lock" only triggers if the attacker already has a guest_session
   346→  cookie — a fresh attacker has none, so the lock is a no-op. The invitation
   347→  code is supposed to be the guest's secret; this chain replaces it with "knows
   348→  a 2-letter prefix of any guest's name + the wedding slug".
   349→FIX: (a) Add IP-based rate limit to /api/guest/lookup (e.g. 5/15min/IP).
   350→  (b) Require an additional proof-of-knowledge before issuing a lookupToken
   351→      (e.g. invitation code prefix or couple's last name).
   352→  (c) Cap lookupToken validity to 60 seconds and bind to the full IP (not /24).
   353→  (d) After 3 successful auto-auths per IP per wedding per day, require
   354→      invitation-code re-verification.
