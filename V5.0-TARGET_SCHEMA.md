### Docker Compose addition
```yaml
services:
  postgres:
    image: postgres:16-alpine
    container_name: wedding-postgres
    restart: unless-stopped
    environment:
      POSTGRES_DB: wedding
      POSTGRES_USER: wedding
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - wedding-postgres-data:/var/lib/postgresql/data
      - ./postgres/init.sql:/docker-entrypoint-initdb.sql:ro  # enables pg_stat_statements
    networks:
      - wedding-network
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U wedding -d wedding"]
      interval: 10s
      timeout: 5s
      retries: 5
    deploy:
      resources:
        limits: { memory: 1G, cpus: '1.0' }
        reservations: { memory: 256M, cpus: '0.25' }
    logging:
      driver: json-file
      options: { max-size: "10m", max-file: "3" }
    security_opt: [no-new-privileges:true]

volumes:
  wedding-postgres-data: { driver: local }
```

### `postgres/init.sql`
```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
CREATE EXTENSION IF NOT EXISTS pg_trgm;        -- trigram index for guest search
CREATE EXTENSION IF NOT EXISTS unaccent;       -- accent-insensitive search (Josué vs Josue)
ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statements';
ALTER SYSTEM SET statement_timeout = '30s';    -- hard cap on slow queries
ALTER SYSTEM SET lock_timeout = '5s';          -- prevent deadlocks stalling
ALTER SYSTEM SET log_min_duration_statement = '500ms';  -- log queries > 500ms
```

### 2.4 Connection pooling (PgBouncer)
Optional but recommended for high-concurrency RSVP scenarios:
```yaml
pgbouncer:
  image: edoburu/pgbouncer:latest
  container_name: wedding-pgbouncer
  environment:
    DB_HOST: wedding-postgres
    DB_PORT: 5432
    DB_USER: wedding
    DB_PASSWORD: ${POSTGRES_PASSWORD}
    DB_NAME: wedding
    POOL_MODE: transaction
    MAX_CLIENT_CONN: 200
    DEFAULT_POOL_SIZE: 10
  ports:
    - "127.0.0.1:6432:5432"
  networks: [wedding-network]
```

App `DATABASE_URL` then points at PgBouncer (`wedding-pgbouncer:5432`) instead of PostgreSQL directly.

### 2.7 CHECK constraints (new in PostgreSQL target)
```sql
-- Email format check
ALTER TABLE "Organization" ADD CONSTRAINT organization_email_format
  CHECK ("email" ~* '^[A-Za-z0-9._%-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$');

-- Slug format check
ALTER TABLE "Wedding" ADD CONSTRAINT wedding_slug_format
  CHECK ("slug" ~* '^[a-z0-9][a-z0-9-]{0,118}[a-z0-9]$');

ALTER TABLE "Organization" ADD CONSTRAINT organization_slug_format
  CHECK ("slug" ~* '^[a-z0-9][a-z0-9-]{0,118}[a-z0-9]$');

-- Capacity positive check
ALTER TABLE "Table" ADD CONSTRAINT table_capacity_positive
  CHECK ("capacity" > 0 AND "capacity" < 1000);

-- Seats positive check
ALTER TABLE "Guest" ADD CONSTRAINT guest_seats_positive
  CHECK ("seats" > 0 AND "seats" < 20);

-- Phone format (loose)
ALTER TABLE "Guest" ADD CONSTRAINT guest_phone_format
  CHECK ("phone" IS NULL OR "phone" ~ '^\+?[0-9 +()-]{6,20}$');
```

## 3. MIGRATION STRATEGY (see V5.0-S04 for full plan)

### Phase A — Schema setup (idempotent)
1. Deploy `wedding-postgres` container
2. Run `prisma migrate deploy` against the new PostgreSQL DB — but migrations are SQLite-specific. Solution: create a new migration directory `prisma/migrations-postgres/` with translated migrations, or use `prisma db push` for initial bootstrap.
3. Verify schema with `prisma db pull` and diff against schema.prisma.

### Phase B — Data migration (with verification)
1. Capture SQLite source row counts + per-table checksums (V5.0-S05)
2. Write ETL script: SQLite → JSON → PostgreSQL bulk insert (use `COPY FROM STDIN`)
3. Per-table: source count == destination count, sample rows match
4. Verify FK integrity in PostgreSQL (`prisma migrate resolve` + custom queries)

### Phase C — Application cutover
1. Build Docker image with new `DATABASE_URL` env (PostgreSQL connection string)
2. Tag previous image as `wedding-platform-app:rollback-pre-v50-pg`
3. SQLite DB backup snapshot preserved (volume rename `wedding-platform_wedding-db` → `wedding-platform_wedding-db-sqlite-snapshot`)
4. Deploy new image; tail `/api/health` for DB status
5. Smoke test all critical flows (V5.0-S26)

### Phase D — Rollback readiness (preserved ≥30 days)
- SQLite volume snapshot preserved on disk
- Previous Docker image tagged
- `rollback.sh` script: `docker stop wedding-app && docker tag wedding-platform-app:rollback-pre-v50-pg wedding-platform-app:latest && docker compose up -d app && curl /api/health`

## 4. POST-MIGRATION HARDENING (V5.0-S07)

### 4.1 Statement timeout
- `statement_timeout = 30s` (system-level)
- Per-query `SET LOCAL statement_timeout = '5s'` for hot paths if needed

### 4.2 Lock timeout
- `lock_timeout = 5s` (system-level)
- Prevents long-running transactions from blocking RSVP writes

### 4.3 Slow query logging
- `log_min_duration_statement = 500ms` — all queries > 500ms logged
- `pg_stat_statements` for top-N slowest queries by total time

### 4.4 Connection pool
- PgBouncer in transaction mode (200 max client conns, 10 pool size)
- App `DATABASE_URL` points to PgBouncer (`wedding-pgbouncer:5432`)

### 4.5 Query analysis
- `EXPLAIN ANALYZE` on top-10 slowest queries from `pg_stat_statements`
- Add indexes based on actual usage patterns

### 4.6 Backup (PostgreSQL-native)
- `pg_dump` daily at 02:00 WAT (replaces `backup-db.sh` SQLite copy)
- `pg_basebackup` weekly for full cluster snapshot
- WAL archiving to off-host location (V5.0-S14 off-host copy)

## 5. EXPECTED PERFORMANCE GAINS

| Workload | SQLite (current) | PostgreSQL (target) | Improvement |
|---|---|---|---|
| Single wedding P95 RSVP write | 50-150 ms (busy_timeout wait) | 5-15 ms (MVCC, no global lock) | 10× |
| Concurrent RSVP across 10 weddings | serialized | parallel | up to 10× throughput |
| Guest search (LIKE '%name%') | O(N) full scan per wedding | O(log N) with pg_trgm GIN index | 5-50× depending on N |
| Audit log query (last 30 days platform) | full table scan | index range scan | 100×+ |
| Settings JSON query | parse string + filter | native JSONB operators + GIN index | 10× |
| Cross-tenant admin dashboard | full table scans per org | proper indexes | 5× |

## 6. ROLLBACK SAFETY

### Preserved during migration
1. SQLite volume snapshot (`wedding-platform_wedding-db-sqlite-snapshot` volume, ≥30 days)
2. Previous Docker image (`wedding-platform-app:rollback-pre-v50-pg`)
3. Previous Git SHA (`6cdb23a7d58abe79f1a51c4644cffe24eb49cc29`)
4. Previous `DATABASE_URL` env (stored in `.env.pre-v50-pg.bak` with 0600 perms)
5. Previous nginx config (already in git)
6. Previous backup script (`backup-db.sh` preserved as `backup-db.sh.pre-v50-pg`)

### Rollback procedure (V5.0-S23 details)
```bash
# 1. Stop the app
docker stop wedding-app

# 2. Revert Docker image
docker tag wedding-platform-app:rollback-pre-v50-pg wedding-platform-app:latest

# 3. Restore .env
cp .env.pre-v50-pg.bak .env
chmod 600 .env

# 4. Start app
docker compose up -d app

# 5. Verify health
curl -k https://wedding.hpph.net/api/health
# Expect: {"status":"ok","checks":{"database":{"status":"ok"}}}

# 6. Verify production weddings still render
curl -k https://wedding.hpph.net/w/pilot-001-org-aline-bertrand
curl -k https://wedding.hpph.net/w/pilot-002-org-chantal-didier
curl -k https://wedding.hpph.net/w/josue-hornella
```

## 7. ITEMS NOT MIGRATED IN V5.0 (deferred to V5.1)

- Read replicas for read scaling (PostgreSQL streaming replication)
- PostGIS for venue geospatial queries (currently `venueLat`/`venueLng` stored as String)
- Full-text search migration to `tsvector` (currently pg_trgm is sufficient)
- Cross-datacenter replication
- Point-in-time recovery (PITR) via WAL archiving (basic version only in V5.0)
- Per-tenant database sharding (still single shared PostgreSQL cluster)
- Materialized views for platform dashboard stats

These are explicitly out of V5.0 scope; current PostgreSQL target is sufficient for 1,000+ weddings.
