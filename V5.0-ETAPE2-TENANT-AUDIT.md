## 1. Architecture Discovery

The codebase has a **3-tier Prisma client architecture** (defined in `src/lib/db.ts`):

| Client | Purpose | Tenant Safety |
|---|---|---|
| `db` | Raw PrismaClient for platform models (Wedding, AdminUser, AuditLog, Organization, Plan, Deployment, PlatformTheme, Template, ...) | Caller MUST manually add `weddingId` for tenant-scoped models |
| `tenantDb` | `db.$extends(tenantScopedExtension)` — auto-injects `weddingId` into findMany/findFirst/count/groupBy/aggregate/create/createMany/updateMany/deleteMany when called inside `runWithTenant()` | Safe — auto-scoped |
| `unsafePlatformDb` | Explicit alias for `db` — signals intentional cross-tenant access | Visible in code review |

### Tenant-scoped models (require `weddingId`)
`guest, table, media, settings, theme, musicTrack, eventTimeline, coupleStory, guestSession, guestAccessLog, invitation, guestGroup, guestbookEntry, programItem, family, gift`

### Platform-level models (no tenant scope needed)
`wedding, organization, organizationMember, adminUser, auditLog, plan, deployment, platformTheme, template, brand, layout, product, customer, deal, payment, subscription, invoice, entitlement, credit*, passwordResetToken, deliveryJob, deliveryAttempt, lead, designVersion, collection*, weddingCollectionBinding, experience*, pricingConfig`

### Important behaviour notes (from `src/lib/db.ts`)
- `tenantDb` does NOT auto-inject on `findUnique / update / delete / upsert` (by-id operations) — callers must use `findFirst` OR add `weddingId` explicitly to `where`.
- `runWithTenant()` AsyncLocalStorage sets the current weddingId context for `tenantDb` to auto-inject.
- SQLite WAL mode is enabled by default (`PRAGMA journal_mode=WAL`) for better write concurrency — critical for multi-wedding RSVPs.

## 3. Defence-in-depth Pattern (the 25 MEDIUM routes)

These routes use raw `db` for tenant-scoped models, but follow the documented safe pattern:

```ts
// 1. Extract weddingId from URL params
const { id: weddingId } = await params;

// 2. Auth check via assertWeddingAccessAsync (denies if user lacks org membership
//    OR doesn't own this wedding)
if (!(await assertWeddingAccessAsync(user, weddingId))) {
  return forbidden('Accès refusé à ce mariage');
}

// 3. Every query has explicit where: { weddingId }
const families = await db.family.findMany({
  where: { weddingId },
  select: FAMILY_SELECT,
});
```

The code explicitly comments on this approach:
> "this route uses the raw `db` client with EXPLICIT `weddingId` filters on every query — defence-in-depth (the same pattern used by the existing /api/weddings/[id]/* routes that built successfully in build 11). This is functionally equivalent to tenantDb-with-auto-inject"

## 4. Recommendations for Étape 6 (Tenant Isolation Hardening)

The audit reveals a robust existing architecture. V5.0-S08 (Tenant Isolation Hardening) should focus on:

1. **Migrate MEDIUM routes to `tenantDb`** — convert the 25 routes that use raw `db` + manual `weddingId` to use `tenantDb` + `runWithTenant()` for auto-injection. This is a defensive refactor (no behaviour change) but reduces the risk of future bugs (a new query added without `where: { weddingId }` would silently leak).

2. **Keep `unsafePlatformDb` for true cross-tenant admin queries** — already explicit and visible in code review.

3. **Add integration tests** for HTTP verb × cross-tenant attempt matrix (V5.0-S22 E2E will cover this):
   - GET/POST/PUT/PATCH/DELETE on /api/weddings/{A_id}/guests with token of org owning wedding B → 403 expected
   - GET/POST/PUT/PATCH/DELETE on /api/weddings/{A_id}/media with token of org owning wedding B → 403 expected
   - Same for /api/guests/{id}, /api/media, /api/tables, /api/timeline, /api/couple-story, /api/settings

4. **Verify `findUnique`/`update`/`delete` by-id operations always include `weddingId`** — since `tenantDb` extension does NOT auto-inject on these. This is a known sharp edge from the code comment.

5. **No CRITICAL issues to fix** — current state is production-safe.
